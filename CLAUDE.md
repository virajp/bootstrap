# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with
code in this repository.

## Purpose

This repository is the source of shared files for other repositories. It has
no build, no tests, and no application code. Other repositories copy files from
it with their own `setup:configs` task. Read `README.md` for the sync contract.

## Layout rule

All shared files are in `tools/<tool>/`, one folder for each tool. The files
at the root (`README.md`, `CLAUDE.md`, `sync.md`) are for this repository
only.

This repository is also a consumer of its own `base` tool. Its values file is
`.config/repo-config.toml`, and `setup:configs` writes the synced copies at
the root (`.config/`, `.gitignore`). Do not edit a synced copy. Change the
file in `tools/<tool>/`, push it, then run `mise run setup:configs` here too.

Each file in `tools/<tool>/` is at the path that it gets in a consumer
repository. For example, `tools/base/.config/mise/tasks/code/merge/develop`
becomes `.config/mise/tasks/code/merge/develop` in a consumer.

- Each tool folder has a `tool.toml` with four keys: `depends`, `root_only`,
  `extensions` and `seed`. All four keys are necessary, because the sync
  reads them without defaults.
- Two tools must not ship the same path.
- A file that the consumer owns after the first write is a seed. List it in
  `seed`.
- Each file that is not a seed starts with this header, in the comment syntax
  of the file (after the shebang in a script, after `---` in YAML, inside `{`
  in JSONC, as an HTML comment in Markdown):

  ```text
  # Synced from repo-config: tools/<tool>/<path>. Do not edit this file.
  # The next sync replaces it, and a manual change is lost.
  ```
- A tool can add `[[precommit]]` tables to its `tool.toml`. Each table is one
  `repos:` entry of `.config/pre-commit-config.yaml`, with its
  `[[precommit.hooks]]`. This key is optional.
- A tool ships its dev-only mise config as `conf.d/<topic>/mise.dev.toml`. The
  sync writes it as `mise.toml` when the consumer lists the tool in
  `core_tools`.

Some files refer to files that are not in `tools/`, for example
`dprint.jsonc`. The consumer repository supplies them.

## How the sync operates

- `tools/base/.config/mise/tasks/_scripts/repo-sync` defines `repo_sync`.
  The consumer task `setup:configs` sources its own copy of that file.
- `repo_sync` reads `tools` from the consumer file `.config/repo-config.toml`.
  It does a shallow clone of the default branch of this repository over SSH.
  Then it adds the `depends` of each tool, and copies each file of each tool.
- gomplate reads the TOML files: the values file and each `tool.toml`.
- The sync never deletes a file, except the merge tasks of the other branch
  model (see "Branch model in the merge tasks"). `sync.md` tells consumers
  what to delete.
- The sync uses the pushed `main` branch. Local changes have no effect on
  consumers until you push them.
- To test a change before you push it, set `REPO_SYNC_URL` to a local clone
  with a commit of the change. Use `repo_sync --dry-run` to show a diff.
- The sync writes the shared `.gitignore` first. Then it adds the lines of the
  consumer file `.config/repo-sync/gitignore`.
- `base` renders `.config/pre-commit-config.yaml` from the `[[precommit]]`
  tables of the selected tools. Then it adds the entries of the consumer file
  `.config/repo-sync/pre-commit.yaml`.

## Templates (`*.tmpl`)

- gomplate renders each `.tmpl` file. The output file has no `.tmpl` suffix.
- The output file takes the git mode of the `.tmpl` file. Make a `.tmpl` that
  renders a task or a script executable (`755`).
- The delimiters are `<% %>`. Do not use `{{ }}` or `[[ ]]` for template
  logic. mise uses `{{ }}` and bash uses `[[ ]]`, and both must reach the
  output unchanged.
- The values come from the consumer file `.config/repo-config.toml`. The
  keys are in `sync.md`, step 3.
- `.members` is the list of member names: the git submodules (else the
  `MEMBERS` env value), then each `[member.<name>]` key with a folder in the
  consumer repository.
- `.tools` is the list of the selected tools. `.extensions` is the sorted list
  of their VS Code extensions. `.precommit` is the list of their
  `[[precommit]]` tables, then the consumer's own entries.

## Task scripts

Task scripts are in `tools/<tool>/.config/mise/tasks/`. mise uses the directory
path
as the task name, for example `code/merge/develop` is `code:merge:develop`. A
`_default` file is the task for the directory name.

- `_scripts/` contains libraries, not tasks. Each task sources them through
  `${MISE_PROJECT_ROOT}/.config/mise/tasks/_scripts/<name>`.
  - `helpers`: the print functions (`print_header`, `print_success`,
    `print_wait`, and others), `members`, and `shell_files_in_scope`. Use these
    functions for all task output.
  - `checks`: git predicates. They return an exit status only and print
    nothing.
  - `merge`: `merge_to_destination_branch`, which the `code:merge` tasks
    use.
  - `placeholder`: for a task that no stack fills yet. A placeholder task
    contains the `#PLACEHOLDER` marker and always exits 0. A stack overlay
    replaces the file. Do not edit a placeholder in place.
  - `repo-sync`: the sync function.
- Prefix each tool call with `mise x --`, for example `mise x -- dprint check`.
  To find whether a tool is available, use `mise x -- which <tool>`, not
  `command -v`. System commands (`git`, `awk`, `sed`) and `mise` itself do not
  get the prefix.
- To find whether the repository has an optional task, use `has_own_task` and
  `own_tasks` from `helpers`. Do not use `mise tasks info` or a wildcard
  `mise run`. In a submodule, mise also finds the tasks of the root
  repository, and it runs them in the root directory.
- Write shell for bash 3.2 and bash 5.x. macOS has bash 3.2 as `/bin/bash`. Do
  not use namerefs, `${var,,}`, or associative arrays.
- Tasks use `#MISE` and `#USAGE` header comments for metadata and flags. A
  `#USAGE flag "--fix"` is available in the script as `usage_fix`.
- Under `set -e`, write a command substitution that can fail as
  `VAR=$(cmd) || VAR=''`. The existing scripts explain this in comments.
- Only the `init` task is in mise config (`_task/mise.dev.toml`). It makes the
  task scripts executable.

## Task output: headers and subheaders

An orchestrator is a task that runs other tasks with `mise run`. A leaf is a
task that runs only commands.

1. A task first checks whether it applies. If it does not apply, it prints
   nothing and exits 0. For example, `setup:deps:python` without a
   `pyproject.toml`.
2. A leaf prints `print_header` first, and only once. Nothing comes before
   it.
3. Each later step of a leaf that needs separation is a `print_subheader`.
4. Status lines (`print_wait`, `print_success`, `print_info`, `print_warn`,
   `print_error`) go under a header or a subheader. They never replace one.
5. An orchestrator prints nothing for a `mise run`. The subtask prints its own
   header. Exception: before `mise run --cd <member>`, it prints a header that
   names the member, because a member is a separate repository.
6. A group of commands in an orchestrator is its own subtask, for example
   `setup:linter`. A single direct command in an orchestrator gets a
   `print_header`, because it is at the level of the sibling subtasks.
7. The top-level orchestrator ends with `line_sep1` and
   `print_success "<Done message>"`, not with a header.
8. Header and subheader text is an "-ing" verb phrase with " ..." at the end,
   for example "Installing pre-commit hooks ...".
9. A task that runs only inside a git hook (`code:graph`, `code:git-config`)
   prints status lines only, no header.

## Branch model in the merge tasks

The branches `main` and `develop` select the model. A branch counts if it
exists locally or on `origin`. `repo_sync` writes the merge tasks of the model
that it finds, and removes the others. It stops if neither branch exists.

- `main` and `develop`: work starts on feature branches.
  `code:merge:develop <branch>` lands a branch on `develop`.
  `code:merge:main` lands `develop` on `main`. Nothing merges from `main`.
  Only `develop` merges into `main`.
- Only one of them: `code:merge <branch>` (`code/merge/_default`) lands any
  feature branch on that branch.
- Merges use `--no-ff`. A hook pass over all files runs first as a safety net.
- `MERGE_MODEL_DEVELOP` and `MERGE_MODEL_MAIN` select `direct` (local merge and
  push) or `pr` (push and open a pull request with `gh` or `glab`). The
  `github` and `gitlab` tools install these CLIs.

## mise config

- `tools/base/.config/mise.toml` holds the shared `[settings]`.
- `conf.d/<topic>/` holds one topic each. `mise.toml` files are for all
  environments. `mise.dev.toml` files are for development only.
- `base` ships the directories with a `_` prefix (`_base`, `_env`, `_task`)
  and `pre-commit`. Each other tool ships `conf.d/<tool>/`.
- A consumer keeps its own mise config in `conf.d/repo/`. No tool ships that
  directory.

## Change a shared file

1. Change the file in `tools/<tool>/`.
2. Commit and push to `main`.
3. In this repository and in each consumer repository, run
   `mise run setup:configs`, then commit the result.
