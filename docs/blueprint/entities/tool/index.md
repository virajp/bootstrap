# Entity: Tool

## Purpose

The tools form a read-only catalog that is versioned with bootstrap and never
stored in the target repository.

Used by: [Setup repository](../../flows/cli/110-setup-repository/index.md),
[Add a tool](../../flows/cli/140-add-tool/index.md),
[Remove a tool](../../flows/cli/150-remove-tool/index.md),
[Select tools](../../flows/cli/160-select-tools/index.md),
[Show the setup](../../flows/cli/170-show-setup/index.md),
[Home](../../flows/site/100-home/index.md),
[Documentation](../../flows/site/110-documentation/index.md).

Scale: 51 tools at 1.0; grows only with new bootstrap releases.

## Out of Scope

- User-defined or repository-local tools.
- Per-file selection inside a tool; the tool is the unit of selection.
- Test tasks, scheduled workflows, deploy files, project tasks (`p:<id>:*`),
  language servers and the project structure of a mobile repository: vwf owns
  them, not bootstrap.
- Running the Apple tools on a host that is not macOS (see Host-only tools).

## Lifecycle / State Machine

N/A — immutable catalog shipped with bootstrap. Contents change only with a new
bootstrap release.

### Engines {#engines}

An engine is a type of runtime, not a catalog tool: it has no row, is never
selected, recorded or named on the command line, and exists only as the `engine`
field of its runtime tools and as a requirement of other tools. Each engine has
a default runtime and a `max`, how many of its runtimes a repository can select
at once:

| Engine       | Runtimes (`engine` value)        | Default   | Max    |
| ------------ | -------------------------------- | --------- | ------ |
| `javascript` | `node`, `bun`                    | `node`    | `many` |
| `java`       | `openjdk`, `corretto`, `temurin` | `openjdk` | `one`  |
| `dart`       | `dart`, `flutter`                | `dart`    | `many` |
| `python`     | `python`                         | `python`  | `one`  |
| `swift`      | `swift`                          | `swift`   | `one`  |
| `ruby`       | `ruby`                           | `ruby`    | `one`  |

`openjdk`, `corretto` and `temurin` are separate runtimes, each pinned the way
mise pins that vendor's Java (for example `temurin-25`); they share mise's
`java` key, so `java` is `max: one`. `flutter` is a `dart` runtime that itself
requires the `java` engine. `kotlin`, `android-sdk`, `xcode`, `jq` and `yq` are
runtimes of no engine.

**Engine `max`.** A `max: one` engine never holds two selected runtimes: two of
its runtimes named in one request (init `--tool`, add) exit 2, and selecting
another runtime while one is held is a replacement, with the consent of a
`max: one` category replacement ([Tool category](../tool-category/index.md)
invariant 3): `--replace` in init and add (without it, exit 2), the "replace
`<old>` with `<new>`?" prompt in the tui. The engine links of the held runtime
move to the new one, as in `add <runtime> --replace` below. In a `max: many`
engine another runtime is kept alongside the held one unless `--replace` is
given (Requires and dependencies).

### Package managers {#package-managers}

A `package-manager` tool installs the dependencies of the runtime(s) it runs on,
and requires that runtime or its engine, so it never dangles: `pnpm` and `yarn`
require `node`; `uv` the `python` engine; `gradle` and `maven` the `java`
engine; `spm` the `swift` engine; `cocoapods` the `swift` engine and the `ruby`
engine (mise pins it as `gem:cocoapods`, and its gem backend needs Ruby). A
runtime's built-in manager is part of the runtime and has no row: `npm` of
`node`, `bun`'s own, `pub` of `dart` and `flutter`, `pip` of `python`, `gem` of
`ruby`.

Each package manager supplies its dependency tasks `setup:deps:<verb>:<tool>`
(`install`, `audit`, `outdated`) and `upgrade:deps:<tool>`, named after the tool
that supplies them. A built-in manager's tasks come with its runtime, under the
runtime's name: `node` (runs `npm`), `bun`, `dart` and `flutter` (run `pub`),
`python` (runs `pip`), `ruby` (runs `gem`). A selected package manager takes
over only the runtime(s) whose packages it installs: `pnpm` and `yarn` take over
`node`'s `npm` tasks, and `uv` takes over `python`'s `pip` tasks. While such a
package manager is selected, the runtime's built-in manager task files
(`tasks/setup/deps/<verb>/<runtime>`, `tasks/upgrade/deps/<runtime>`) are not
rendered (see Selection-dependent files), so only the package manager's
dependency tasks run; the dispatchers still never test which tools are present.
`cocoapods` requires the `ruby` engine only for its own install and does not
take over `ruby`'s `gem` tasks. `gradle`, `maven`, `spm` and `cocoapods` run on
runtimes with no built-in manager tasks (the `java` runtimes, `swift`), so they
have nothing to take over. `spm` resolves the packages of both `Package.swift`
and Xcode projects. The other runtimes (`kotlin`, `android-sdk`, `xcode`,
`swift`, the `java` runtimes, `jq`, `yq`) supply no dependency task.

`swiftlint` and `swift-format` are installed by mise (they have pins), but run
only on macOS, so they carry `host_os` without `host_only`. `spm` ships inside
the Swift toolchain, so it is host-only like `swift`. Every tool that requires
the `swift` engine runs only on macOS (invariant 15), `cocoapods` included.

**Host-only.** A `host_only` tool is one mise cannot install: it has no pin and
no mise entry, and every task that needs it first checks it is present
([tool-versions](../../conventions.md#tool-versions)). A tool with `host_os`
runs only on that operating system. Selecting a tool with `host_os: macos` on a
host that is not macOS is refused in init, add and the tui (exit 2,
[errors](../../conventions.md#errors)); only a new selection is refused, so a
recorded one stays selected and renders on any host. Its tasks fail with exit 1
on a host that is not macOS; such a repository runs those gates on macOS
runners.

**Extensions.** `.vscode/extensions.json` is built from the `vscode_extensions`
of every selected tool (see Selection-dependent files); the list is an input of
the catalog, not typed by users. Several tools may declare one extension; the
file lists it once.

**Container engine.** `docker` is not a catalog tool. The `local-services` tools
that run containers (`firebase`, `temporal`, `grafana`) do not require a tool
for it: their tasks check that a container engine (`docker`) is present, and
each declares the Docker extension.

**Renames.** `renamed_from` lists the old catalog names of a tool; none exists
in 1.0. A recorded old name is read as the new one and rewritten as a repair of
the setup file ([Repair on read](../setup-config/index.md#repair)): a change
that needs consent, reported with the warning "renamed tool `<old>` to `<new>`".
A rename of a pinned package inside a tool (its pin line changes identity) is a
new pin, per [tool-versions](../../conventions.md#tool-versions).

### Requires and dependencies {#requires-and-dependencies}

`requires` is a list of requirements. Each names either one tool (in the
Requires column, for example `uv`) or one engine (for example engine `python`).
The tools and their requirements form a graph in which a selected tool connects
to any number of tools but never dangles: every requirement of every selected
tool is met.

- A **tool requirement** is met while that tool is selected.
- An **engine requirement** is met while at least one runtime of that engine is
  selected. The tool is linked to one such runtime: the runtime recorded with it
  as a parent, else a runtime selected directly. When none is selected, the
  engine's default runtime is added and linked.

A tool that a selected tool requires, or a runtime added for an engine
requirement, that the user did not select directly is a dependency. A dependency
is installed and rendered like any selected tool and is recorded with its
parents in the [Setup config](../setup-config/index.md). A dependency with no
parent left is pruned: an added runtime leaves when the last tool linked to it
leaves; a runtime the owner selected directly stays.

**Dangling rule.** When a tool leaves the selection, every selected tool that
would then dangle leaves with it: one that requires the leaving tool, or that
requires an engine whose last selected runtime is leaving, and so on
transitively (when `node` leaves, `pnpm`, `yarn` and every tool that needs only
the `javascript` engine through `node` leave too). A runtime can leave without
taking anything when another runtime of the same engine stays selected for each
of its parents; their links move to that runtime. A tool never leaves this way
without consent: the CLI exits 2 naming every direct tool that would dangle, and
its next command is the same command plus those tools (naming them in the same
request removes them all; when one of them is unremovable there is no next
command); the tui names them all in one prompt, "remove `<parent>` too?"
([Select tools](../../flows/cli/160-select-tools/index.md)). A dependency that
would dangle is pruned with them.

The `requires` check, per request ([errors](../../conventions.md#errors)):

### Target paths (1.0)

Paths are relative to the target repository root, where bootstrap writes them.
`tasks/` stands for `.config/mise/tasks/` and `conf.d/` for
`.config/mise/conf.d/`. File contents are not part of the contract, except
invariants 5 and 6, the dispatcher behaviour under Task dispatchers (what each
`_default` runs, "no tool", exit 0), the mise entries and behaviour listed for
the files below and the selection-dependent files below. A file marked
`create_only` is written only when absent
([safety](../../conventions.md#safety)); every other file is shared, universal
and re-rendered by every run. The `create_only` files are exactly: `.gitignore`,
`.graphifyignore`, `.config/linter.yaml`, `.config/gitleaks.toml`,
`.config/grype.yaml`, `.config/ktlint.editorconfig`, `.config/detekt.yml`,
`.config/swiftlint.yml`, `.config/swift-format.json`, `.npmrc`,
`.config/fnox.toml`, `doppler.yaml`, every compose and image file of a
`local-services` tool, and firebase's `firebase.json`, `.firebaserc`, rules and
index files. The setup config `.config/bootstrap.yaml` belongs to no tool; init,
add, remove, scope, member and the tui write it. Every tool with a mise pin
renders its exact pin in `conf.d/<tool>/mise.toml` and `latest` in
`conf.d/<tool>/mise.dev.toml`
([tool-versions](../../conventions.md#tool-versions)). That pin pair is implied
for every pinned tool and no row lists it; the rows name only the entries beyond
it. One exception: `osv-scanner` is pinned exactly in
`conf.d/osv-scanner/mise.toml` only, with no dev file, so it is exact in every
environment (decided 2026-10-09).

`tasks/external/<verb>/<tool>` in a row stands for the four verbs `start`,
`stop`, `upgrade` and `cleanup`; `tasks/setup/deps/<verb>/<tool>` stands for the
three verbs `install`, `audit` and `outdated`.

Behaviour pinned for the `pre-commit` row, in `.config/pre-commit-config.yaml`:

- Hooks present: the format and lint hooks (the lint hook with
  `require_serial`), the no-dash-names hook, the check hook (runs `code:check`),
  and the two manual meta-audit hooks. No hook normalises `package.json` through
  npm.
- `check-json` skips `tsconfig*.json` and `.vscode/`; `trailing-whitespace`
  skips markdown; `check-yaml` allows multiple documents;
  `check-added-large-files` skips `mp4`, `wav` and `m4a`.
- The graph refresh runs at the post-merge hook only (after a merge or pull),
  never at post-commit.

bootstrap writes no `.gitattributes`, no `.claude/hooks/` and no
`.claude/settings.json`.

Mise entries go in the env file they belong to (`mise.toml`, `mise.dev.toml`,
`mise.ci.toml`); a setting lives with the tool it applies to. Besides the tool
folders, `conf.d/` holds files owned by the `mise` tool:

- `conf.d/env.toml`: the product env values `MEMBERS` (the slugs of
  `values.members`), `MERGE_MODEL_DEVELOP`, `MERGE_MODEL_MAIN` and `REPO_NAME`;
  `conf.d/env.<env>.toml` holds values specific to one `MISE_ENV` (none in 1.0).
- `conf.d/task-init.dev.toml`: the `init` task.
- `conf.d/alias.dev.toml`: the shell aliases `setup` and `worktrees`.

Mise-wide settings stay in `.config/mise.toml`.

The data of a local service is shared across repositories in
`~/.local/share/<service>/`, and its compose name is the service name, so every
repository drives the same containers.

### Task dispatchers

A `_default` file under a task folder defines the folder's task
(`tasks/code/sec/_default` is `code:sec`) and runs every per-tool subtask
present in that folder (`code:sec:gitleaks`, `code:sec:grype`,
`code:sec:osv-scanner`); with none present it prints "no tool" and exits 0. The
hook tasks are dispatchers too, owned by `mise`:
`tasks/setup/git-hooks/_default` (`setup:git-hooks`) and
`tasks/code/git-hooks/_default` (`code:git-hooks`). Each git-hooks tool supplies
its subtasks; `pre-commit` supplies `setup:git-hooks:pre-commit` and
`code:git-hooks:pre-commit`. The `precommit` shell alias stays with `pre-commit`
(a replacing tool brings its own alias). The `code:graph` dispatcher is run by
the post-merge hook, and no task runs `graphify hook install`; the git-hooks
setup runs once per `setup:all` and still removes raw hooks with
`graphify hook uninstall`.

The task groups, all dispatchers that call the per-tool subtasks and never test
which tools are present:

| Group            | Dispatchers (`<verb>:<tool>` subtasks)                                                                | Behaviour                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `code:*`         | `code:format`, `code:lint`, `code:check` (type checks), `code:sec`, `code:graph`, `code:git-hooks`    | `code:all` runs `code:check`, `code:format`, `code:lint` and `code:sec` in that order; `code:precommit` runs the gates on the changed and untracked files; `code:count` counts all tracked files (top 10 extensions and the total)                                                                                                                                           |
| `setup:*`        | `setup:deps:<verb>` (`install`, `audit`, `outdated`), `setup:secrets`, `setup:git-hooks`, `setup:ai`  | `setup:mise` runs, in order, `mise doctor 1>/dev/null`, `mise install --include-lazy --yes`, `mise upgrade --local --prune --yes` (no `--bump`) and `mise reshim --yes`                                                                                                                                                                                                      |
| `setup:all`      | none                                                                                                  | in order: 1 `setup:mise`; then `setup:secrets`; 2 `setup:deps` (every dependency install is frozen to the lockfile); 3 `external:start`; 4 the git hooks (`setup:git-hooks`) and the AI tools (`setup:ai`) only; the VS Code profile is never set up here: bootstrap updates it after a write ([errors](../../conventions.md#errors)). It never upgrades a lockfile or a pin |
| `setup:worktree` | none                                                                                                  | steps 1 and 2 of `setup:all` only: no secrets, no external services, no hooks, no AI                                                                                                                                                                                                                                                                                         |
| `upgrade:*`      | `upgrade:deps` (`upgrade:deps:<tool>`: each package manager and each runtime with a built-in manager) | `upgrade:mise` moves every exact pin to the newest version (`--bump`); `upgrade:deps` upgrades each package manager's dependencies and lockfile; `upgrade:all` runs `upgrade:mise`, `upgrade:deps` and `external:upgrade`; none of them runs tests                                                                                                                           |
| `external:*`     | `external:start`, `external:stop`, `external:upgrade`, `external:cleanup` (`external:<verb>:<tool>`)  | each verb runs the matching subtask of every selected tool that supplies one (`cloudflare`, `firebase`, `temporal`, `grafana`); `external:cleanup` replaces the old `setup:cleanup`; the tasks of a tool that runs containers check that `docker` is present                                                                                                                 |

`setup:deps` only calls three dispatchers, in order: `setup:deps:install`
(frozen to the lockfile), `setup:deps:audit` and `setup:deps:outdated` (a report
only); each is a `_default` dispatcher over its `setup:deps:<verb>:<tool>`
subtasks like the others: every package manager and every runtime with a
built-in manager (`node`, `bun`, `dart`, `flutter`, `python`, `ruby`) supplies
all three ([Package managers](#package-managers)), and `code:check` has the one
subtask `code:check:uv`. A dispatcher with no subtask for the selection prints
"no tool" and exits 0. It never upgrades or cleans up: upgrades live in
`upgrade:deps`. The `setup/deps/<verb>` and `external/<verb>` and `upgrade/deps`
dispatchers are folders (`tasks/<group>/<verb>/_default`).

### Selection-dependent files {#selection-dependent-files}

Files whose content depends on the selection are re-rendered by every command
that changes the selection. The complete list:

- `.config/git-conventional-commits.yaml`: the commit types are the same in
  every repository (`feat`, `fix`, `perf`, `refactor`, `style`, `test`, `build`,
  `ci`, `docs`, `chore`, `revert`, `merge`, per conventionalcommits.org v1.0.0),
  each with a comment an AI agent reads when it writes a message. The scopes are
  `values.scopes` ([Setup config](../setup-config/index.md)), one per entry, its
  `description` written as the scope's comment. The forge links come from the
  selected forge whose host matches `origin`; if none matches, the first
  selected forge in catalog order; with no forge selected, the file has no forge
  links. The three links are literal URLs (no environment variable) and use
  `<host>`, the host of `origin` (with no readable `origin` host, the forge's
  first `origin_hosts` entry), and `<repo>`, the recorded repository path:

  | Link    | `github`                                                 | `gitlab`                                        |
  | ------- | -------------------------------------------------------- | ----------------------------------------------- |
  | commit  | `https://<host>/<repo>/commit/<sha>`                     | `https://<host>/<repo>/-/commit/<sha>`          |
  | compare | `https://<host>/<repo>/compare/<from>...<to>?diff=split` | `https://<host>/<repo>/-/compare/<from>...<to>` |
  | issue   | `https://<host>/<repo>/issues/<n>`                       | `https://<host>/<repo>/-/issues/<n>`            |
- `dprint.jsonc`: its TOML formatting (the exec plugin and its command that run
  taplo for TOML files) is present only when `taplo` is selected; without taplo,
  dprint does not format TOML files.
- `.claude/skills/mise/SKILL.md`: its task table lists the tasks of the
  selection.
- The built-in manager task files of a taken-over runtime
  ([Package managers](#package-managers)): `tasks/setup/deps/<verb>/node` and
  `tasks/upgrade/deps/node` are rendered only while neither `pnpm` nor `yarn` is
  selected; `tasks/setup/deps/<verb>/python` and `tasks/upgrade/deps/python`
  only while `uv` is not selected.
- `.vscode/extensions.json`: the union of the `vscode_extensions` of every
  selected tool, including the `vscode` tool's own. When a write changes it,
  bootstrap itself syncs the `REPO_NAME` editor profile to it (the one tool it
  runs after a write): it installs every listed extension and uninstalls every
  extension no selected tool lists ([errors](../../conventions.md#errors)); a
  missing `code` command or a failed install or uninstall is a warning, exit 0.
  This is not part of `setup:all`.

`.vscode/settings.json` is not selection-dependent: it holds the keys of every
tool in every repository.

Versions follow [tool-versions](../../conventions.md#tool-versions).

## Invariants

1. No file path appears in more than one tool.
2. A tool with `removable` false is always selected and cannot be removed; if
   shown, it can be replaced in place within each `max: one` category it is in.
3. Every tool of the catalog has at least one category, and every category it
   names exists.
4. A category with `max: one` never holds two selected tools.
5. Every task file is written executable
   ([safety](../../conventions.md#safety)).
6. Every tool a rendered task runs is installed by mise
   ([tool-versions](../../conventions.md#tool-versions)), except the named
   exemptions: `git`, `mise` itself, the AI agent's own CLI (`claude`), the
   `code` command that bootstrap itself runs, the container engine (`docker`),
   whose presence the `local-services` tasks check, and every `host_only` tool.
7. `mise` is the only hidden tool: it is always applied (init, add, remove and
   the tui render its files as for any selected tool), never recorded in
   `values.tools` or `values.dependencies`, and never shown or named in any
   tool-name list (tui, human and `--json` output, `show`), so no request can
   name it (naming it in `init --tool`, `add` or `remove` is an unknown tool
   name), replace it or remove it; `removable: false` implies `default: on`.
8. `origin_hosts` is present only when `default` is `origin`.
9. No two `origin` tools of one `max: one` category share a host.
10. Every tool but `mise` renders its mise entries only into
    `.config/mise/conf.d/<tool>/` (the `mise` tool's own files are listed in its
    Target paths row), and each mise entry declares mise `depends` on the tool
    that meets each requirement it runs on (for an engine requirement, the
    linked runtime), so mise installs them first; a `host_only` tool gets no
    mise `depends` (its tasks check that it is present).
11. Every requirement names a tool of the catalog or an engine of the Engines
    table; no tool requires itself, and the graph of requirements (an engine
    requirement read as an edge to each runtime of that engine) has no cycle.
12. A `max: one` category holds at most one `default: on` tool and at most one
    unremovable tool; every category holds at least one tool.
13. A recorded selection is checked per
    [Validity](../setup-config/index.md#validity) and
    [Repair on read](../setup-config/index.md#repair).
14. A replacement applies only in a `max: one` category or among the runtimes of
    one engine (always in a `max: one` engine, with `--replace` in a `max: many`
    one); elsewhere a tool is added and the other removed.
15. A `host_only` tool has no mise entry and no pin. `host_os` is set only on a
    tool that cannot run elsewhere; a tool that requires a tool with `host_os`,
    or an engine whose every runtime has `host_os`, has the same `host_os`.
16. A name in `renamed_from` is never the current name of any catalog tool and
    appears in the `renamed_from` of one tool only.
17. A tool with the `local-services` category and a container requires no tool
    for the container engine: its tasks check that `docker` is present; its
    compose name equals its name and its files live under `.config/<tool>/`.
18. `engine` is set only on a `runtime` tool, and names an engine of the Engines
    table; every engine has at least one runtime, its default is one of them,
    and a `max: one` engine never holds two selected runtimes.
19. Every `package-manager` tool requires a runtime or an engine (it never
    dangles), and only package managers and the runtimes with a built-in manager
    (`node`, `bun`, `dart`, `flutter`, `python`, `ruby`) supply
    `setup:deps:<verb>:<tool>` and `upgrade:deps:<tool>` subtasks.
20. A selection bootstrap writes never holds a tool with an unmet requirement:
    every writing command applies the Dangling rule (a hand-edited one is
    repaired per invariant 13).
