  <h1>Bootstrap TUI Screens</h1>
  <p class="lede">Draft 43 of the screens of <code>bootstrap tui</code> (repo side) and <code>bootstrap mac tui</code> (Mac side). Nothing is built. Each screen shows its actions and its open points. The sample repository is <code>~/Projects/acme-web</code>. On the cursor row, a name that is longer than its column scrolls. The selection model of the engine is in the artifact "Bootstrap Selection Model".</p>
  <p><code>bootstrap init</code> in a terminal opens the TUI. On a repository with no values file, the TUI starts with the pack <code>base</code> selected, and Apply writes the new values file. With no terminal, or with <code>--no-tui</code>, <code>init</code> selects only <code>base</code> and syncs. On a repository that has a values file, <code>init</code> first runs the migrations of the old forms, for example <code>[packs.*]</code> into tables of tools. Then it opens the TUI with the tools of the values file, the same screen as <code>bootstrap tui</code>. With no terminal, or with <code>--no-tui</code>, it adds the members of <code>base</code> that have no table, asks nothing, and syncs. In a terminal that is smaller than 100 × 25, <code>init</code> stops with code 2 (screen 1). It never goes on as <code>--no-tui</code>. <code>bootstrap tui</code> opens the TUI on a repository that has a values file. The Mac side is the same: <code>bootstrap mac init</code> and <code>bootstrap mac tui</code>.</p>

  <section id="s2">
    <span class="tag">2 · packs · repo and Mac</span>
    <h2>Packs</h2>
    <p>A pack is a shortcut. It adds tools, and the values file keeps no record of it: the file holds only <code>[tools.&lt;name&gt;]</code> tables. The user selects or deselects packs in the left pane only. The left pane shows a mark for each pack: [x] each member is selected, [~] some members are selected, [ ] no member is selected, [+] will add, [-] will remove, [=] the pack <code>base</code>, which the user cannot deselect. The right pane only lists the tools that the pack installs, with the name, the summary and a dim status. It has no selector, and its rows have no action. While the cursor is on a pack in the left pane, the bottom pane shows the name of the pack and its description. A pack has no summary. The cursor can go into the right pane with ← →. There the pane is read-only: the bottom pane shows the details of the member under the cursor (the description, the kind on the Mac, the tools that it needs and the status), and space does nothing.</p>
    <p>A selected or a deselected pack is one change in the counter of the header, and one line in the review.</p>
    <p>On the repo side, <code>base</code> is the only pack. The other repo tools come from the Tools tab or the Detected tab. In this sample, the cursor is in the right pane on <code>vscode</code>.</p>
    <div class="term"><pre id="t2"></pre></div>
    <p>The Mac side has more packs. Here the user deselects the installed pack <code>terminal</code>, so it shows [-] and its two tools will leave. The user also selects the pack <code>media</code>, so it shows [+]. The header shows 2 changes: one for each pack.</p>
    <div class="term"><pre id="t2m"></pre></div>
    <p id="s2toml">The form of <code>repo/packs.toml</code>. Each member is a default: <code>tool = {}</code>, or <code>tool = { required = true }</code> in <code>base</code> only. <code>description</code> is a reserved key. A tool can be in no pack.</p>
    <div class="term"><pre>[pack.base]
description = "The tools of each repository: mise, git, the hooks, the format and lint gates, the security scanners and the VS Code config."
mise = { required = true }
git = { required = true }
pre-commit = { required = true }
dprint = { required = true }
linter = { required = true }
gitleaks = { required = true }
grype = { required = true }
osv-scanner = { required = true }
vscode = {}</pre></div>
    <div class="cols">
      <div><h3>Actions</h3>
        <table>
          <tr><td>space on a pack</td><td>The pack goes on the change list as one change. Select: Apply adds the members that are not selected. Same as: <code>bootstrap add pack P</code>. Deselect of an installed pack: Apply removes each member, except a required member and a member that another selected tool needs. When a tool outside the pack needs a member, the cascade dialog (screen 4) asks first. The CLI has no command for it: one <code>bootstrap remove tool</code> for each member.</td></tr>
          <tr><td>space on [=]</td><td>Nothing. The user cannot deselect <code>base</code>.</td></tr>
          <tr><td>← →</td><td>Go to the other top pane. In the right pane, the bottom pane shows the details of the member.</td></tr>
          <tr><td>space in the right pane</td><td>Nothing. The right pane is read-only. To remove one tool, the user goes to the Tools tab.</td></tr>
        </table>

  <section id="s2b">
    <span class="tag">2b · repo · detected</span>
    <h2>Detected tools</h2>
    <p>Each time the user opens the Detected tab, the TUI runs the detect scripts, as <code>bootstrap detect</code> does. The Mac side also has the Detected tab: it runs <code>bootstrap mac detect</code>. On the command line, <code>bootstrap detect</code> with no flag only lists the detected tools, also in a terminal: it does not open the TUI. It exits with code 1 when a detected tool is not selected, else with code 0. <code>bootstrap detect --add</code> adds each detected tool that is not selected, after the <code>[y/N]</code> consent. <code>--yes</code> answers the consent. The flag <code>--no</code> is gone. A modal dialog shows while the scripts run. <code>esc</code> stops the scripts and goes back to the tab of before, with no change.</p>
    <div class="term"><pre id="t2a"></pre></div>
    <p>Then the tab shows the proposal of the detection. In the right pane, the selector of a proposal shows <code>[?]</code>: the user must make a choice. A green <code>[?]</code> adds the tool, and a red <code>[?]</code> removes it. A proposal is not on the change list, so the counter of changes in the header does not change. The right pane has no ◆. In the left pane, ◆ marks a category with a proposal. On the Tools tab, ◆ also marks such a category, but not the tool row.</p>
    <div class="term"><pre id="t2b"></pre></div>
    <div class="cols">
      <div><h3>Actions</h3>
        <table>
          <tr><td>space</td><td>Accept the proposal of one tool: it goes on the change list, and the green <code>[?]</code> becomes <code>[+]</code>, or the red <code>[?]</code> becomes <code>[-]</code>. Space again takes it off the list, and the mark is <code>[?]</code> again.</td></tr>
          <tr><td>a</td><td>Accept all proposals. They go on the change list. Same as: <code>bootstrap detect --add</code>.</td></tr>
          <tr><td>esc (dialog)</td><td>Stop the detect scripts. Go back to the tab of before.</td></tr>

    <span class="tag">7 · questions</span>
    <h2>A tool needs values</h2>
    <p>The questions form opens in three cases. The user selects a tool with <code>[questions]</code>: the TUI asks each question before the tool goes on the list. The user presses <code>e</code> on a selected tool. Or the user starts Apply: Apply first plans the change list. If a selected tool has a question with no answer in the values file and no answer on the change list, the TUI opens the form for that tool before it writes. It opens one form for each such tool, in the order of the tools. Cancel in such a form stops Apply, and the TUI goes back to the main screen with the change list kept.</p>
    <p>The sample is the form of the Mac tool <code>git</code> at the first Apply of <code>bootstrap mac init</code>. <code>git</code> is a required member of <code>base</code>, and <code>macos.toml</code> has no answers yet. A <code>detect</code> command fills each proposal, for example the GitHub email from <code>gh api user</code>. The form is a modal dialog. The 4 questions do not fit, so the content scrolls: here it is scrolled down, and the dialog shows ▲. A <code>group</code> line says that at least one of the two emails is necessary. A <code>note</code> under the SSH key says that one key signs for both forges. The buttons stay visible.</p>

  <section id="s8">
    <span class="tag">8 · review and apply</span>
    <h2>Review the changes</h2>
    <p>The list of changes, then the file plan of a dry run. A pack is one line. Apply first plans the change list and asks the questions that have no answer (screen 7). Then it writes the values file and runs the sync. This is the only step that writes.</p>
    <div class="term"><pre id="t8"></pre></div>
    <p>After Apply, the TUI shows the output of the sync. Any key goes back to the main screen.</p>
    <div class="term"><pre id="t8b"></pre></div>
    <p>If the sync fails, the TUI puts the values file back as it was before Apply and shows the output. Any key goes back to the main screen with the change list kept. The user can correct the changes and apply again.</p>
    <div class="term"><pre id="t8c"></pre></div>
    <div class="cols">

Then write the values file and run the sync. Show its output (below), then go back to the main screen with an empty change list.</td></tr>
          <tr><td>f</td><td>Show the full file list.</td></tr>
          <tr><td>Back / esc</td><td>Go back to the main screen. The changes stay.</td></tr>
        </table>
