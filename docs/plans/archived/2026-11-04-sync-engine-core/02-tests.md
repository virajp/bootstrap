## Ruling

From the design rulings of 2026-11-04:

> - One header on both sides, the repo form with the new path:
>   `Synced from bootstrap: tools/<side>/<tool>/<path>. Do not edit this file`
>   - `The next sync replaces it, and a manual change is lost`. During the
>     transition the detection (first 3 lines) also accepts `Synced from
>     bootstrap`, `Synced from repo-config` and `Generated by macos-setup`; a
>     later cleanup (with a `migrate.md` step) drops the old texts. Merge
>     sources carry `Merged by bootstrap: <path>` where the format has
>     comments; the engine does not read it.

> - Formatter: the parse check (jq for JSON, yq for YAML/TOML; a target that
>   does not parse → exit 2, old file stays) moves into the shared engine and
>   runs on both sides. The `format` key (`text`/`json`/`yaml`/`toml`,
>   default from the extension) is in the shared `[files]` schema. dprint
>   stays repo-only; repo order: render, parse check, merge, dprint,
>   compare. The Mac does not format.

From this plan:

D3: "This plan extends test:repo-sync with cases for its new rules. A current
case changes only where a ruling changes its expected result."

D6: "A target with the extension .json gets the format json, except when the
rendered file has a line that starts with // after spaces: that file is JSONC
(the bootstrap header of a JSON file is a comment inside {), so its format is
text. .vscode/settings.json and .vscode/extensions.json are such files; jq
cannot read them. A later format key of a [files] table wins over this
default."

D9: "In the first step of the write of each file (today _rs_file), after the
render and after pre-commit autoupdate, before the dprint stage. It runs on
every file that the sync writes or compares: a template render, a plain copy,
a new seed and a generated mise file. A failure prints '<path>: the result
does not parse as <format> - the current file stays', keeps the target as it
is, and gives code 2; the other files go on. A dry run reports the same code."

D15: "On success, the check discards the stdout and the stderr of jq and
yq, so the sync output stays byte equal. yq runs with -p <format> -o json, as
B:1229 does. An empty render of a .json target fails with code 2, as B does."

D18: "With case_args=' ' (test line 550 already runs a real write this way).
No new CASE_REAL variable."

D10: "Every place that reads the bootstrap header today: the unblock of a

## Edits

1. **`.config/mise/tasks/test/repo-sync` — a real run.** A case that needs
   a real write runs with `case_args=' '`, as the fnox seed case (:550) does
   (D18). Add no new variable.
2. **A fixture tool.** A change function adds the folder `tools/fixture/` to
   the scratch clone, with a `tools.toml` of the five keys of today
   (`default_envs = ["dev"]`, `depends = []`, `extensions = []`,
   `root_only = false`, `seed = []`) and the files of each case. A case
   selects it with `[tools.fixture]`. Give each shipped fixture file the
   bootstrap header in the syntax of its format, except where a case needs
   it absent.
3. **Parse-check cases:**
   - "a JSON template that does not parse": `bad.json.tmpl` renders
     `{"a": }`; the consumer has `bad.json` with known content; a real run
     exits 2 with `bad.json: the result does not parse as json`, and
     `bad.json` keeps its content.
   - "a YAML file that does not parse": `bad.yaml` with `a: [`; dry run,
     exit 2, the message names `yaml`.
   - "a TOML file that does not parse": `bad.toml` with `a = `; dry run,
     exit 2, the message names `toml`.
   - "an empty JSON render": `empty.json.tmpl` renders nothing; dry run,
     exit 2 (D15).
   - "a JSON file with comments is text": `ok.json` with a `//` line and a
     trailing comma; dry run, exit 0 (D6).
   - "one bad file does not stop the others": the bad JSON template and a
     good plain file in one tool; a real run exits 2 and writes the good
     file.
4. **Header cases** (D10), each a dry run:
   - For each text `Synced from bootstrap: `, `Synced from repo-config: `
     and `Generated by macos-setup`: a consumer file
     `.config/mise/conf.d/oldtool/mise.dev.toml` with the text on line 2
     (line 1 a plain comment); the output has
     `would remove .config/mise/conf.d/oldtool/mise.dev.toml`.
   - "a file without the header stays": the same file without a header
     text; the output has no `would remove` for it.
5. Every current case passes unchanged. When a current case fails because
   of the parse check of a real bootstrap file, do not change the case:
   report it as an `UNRESOLVED:` with the file and the tool message.
